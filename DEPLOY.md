# Размещение статической игры

```sh
npm ci
npm test
npm run build
```

Разместить содержимое `client/dist/` на статическом хостинге. Главная страница — игра, `?staff=1` — подготовка QR. Относительные пути ресурсов позволяют размещать сборку и в подкаталоге. Открывать через HTTP(S), а не `file://`.

На странице QR указать окончательный публичный адрес, скачать PNG и разместить его на деревянном сундучке с изолентой. `localhost` и локальный адрес разработчика для печатного QR не подходят.

## Существующая ВМ

Workflow `.github/workflows/deploy.yml` срабатывает при push в `main`: устанавливает зависимости по lockfile, запускает тесты, собирает сайт и отправляет только статические файлы в `/opt/honkai-chat/client/dist/`.

Существующий процесс `honkai-chat` заменяется раздачей статики на прежнем порту 3001:

```sh
pm2 serve /opt/honkai-chat/client/dist 3001 --spa --name honkai-chat
pm2 save
```

Это стандартная [раздача статических файлов PM2](https://pm2.keymetrics.io/docs/usage/expose/); серверной логики игры нет. Текущий обратный прокси на порт 3001 можно сохранить. Workflow использует уже настроенные GitHub Secrets `VM_HOST`, `VM_USER`, `VM_SSH_KEY`.

После размещения проверить вход со смартфона, короткий путь до сапёра, обновление вкладки с начатой партией и сканирование распечатанного QR. Старые ссылки `/guest` и `/actor` работают благодаря SPA fallback.
